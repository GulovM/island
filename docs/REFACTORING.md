# ТЗ: разбиение крупных файлов в `src/`

## 1. Цель

Разбить самые раздутые файлы на модули-каталоги по ответственности, чтобы:

- файл открывался и читался целиком, а правка одной подсистемы не задевала соседние;
- в диффах и истории было видно, какая подсистема менялась;
- новые функции (как Wallpaper Engine в `we.rs`) было куда добавлять без разрастания старых файлов.

**Не цель:** менять поведение, интерфейс, формат файлов настроек и данных, список зависимостей.

## 2. Ограничения (приёмка по ним же)

| Что | Требование |
|---|---|
| Поведение | Идентично до и после. Рефакторинг = только перенос кода. |
| Бюджеты ([CONTRIBUTING.md](../CONTRIBUTING.md)) | CPU в простое ≈ 0%, RAM ≤ 30 МБ, exe ≤ 2 МБ. Размер exe не должен заметно вырасти (допуск ±1%). |
| Внешние пути | `crate::sys::foo`, `crate::ui::Ui`, `crate::bg::snapshot` и т. д. продолжают работать — через `pub use` в `mod.rs`. Остальной код менять не нужно, кроме импортов в редких случаях. |
| Тесты | Все существующие тесты (около 140) остаются и проходят. Тесты переезжают в тот файл, где теперь лежит проверяемый код. |
| Зависимости | Новых нет. |
| Сборка | `cargo build --release`, `cargo test`, `cargo clippy --release` — без новых предупреждений. |

`lto = true` и `codegen-units = 1`, поэтому границы модулей не влияют на инлайнинг и скорость.

## 4. Целевая структура

Правило: `foo.rs` → `foo/mod.rs` + подмодули. В `mod.rs` остаются типы и функции, которыми пользуется весь проект, и `pub use` подмодулей. Подмодули пишутся по принципу «одна ответственность — один файл», а не «одна функция — один файл».

## 5. Правила переноса

1. **Один файл за раз, один коммит на файл.** Любой шаг откатывается без последствий.
2. **Чистый перенос.** В коммите нет переименований, смены сигнатур, «заодно поправил». Если по пути виден баг или улучшение — записать в заметки и делать отдельным коммитом после.
3. **Видимость:** по умолчанию приватное; между подмодулями — `pub(super)`; наружу из каталога — `pub use` в `mod.rs`; `pub(crate)` только если действительно нужен остальному проекту.
4. **Тесты уезжают вместе с кодом** (`#[cfg(test)] mod tests` в том же подмодуле).
5. **Документирующие комментарии и стиль сохранить**, комментарии на русском, как в окружающем коде.
6. **`unsafe fn`**: не менять границы `unsafe`. Это касается и вызовов Win32/COM: переносим «как есть».
7. **Порядок файлов:** от наименее связанного кода к наиболее связанному (см. раздел 6). Так каждый шаг проверяется независимо.
8. **Допустимые отклонения от чистого переноса:** (а) блоки `//` в начале подмодуля можно превращать в `//!` документацию модуля; (б) тестовые модули можно объединять и переименовывать в `tests`; (в) импорты пересобираются под каждый подмодуль; (г) удалённые комментарии-заголовки разделов не считаются изменением. Всё остальное (тела функций, сигнатуры, логика) менять нельзя.

## 7. Проверка

**Базовые показатели (до начала):**

- `cargo test` — число тестов и что все зелёные;
- `cargo clippy --release` — число предупреждений;
- размер `target\release\island.exe`;
- быстрый ручной прогон: все 7 вкладок, настройки, плеер, буфер обмена, обои (в том числе WE), будильник, Wi-Fi/Bluetooth списки. Запускать с временным `APPDATA`, чтобы не затронуть свой `config.toml` (см. [CONTRIBUTING.md](../CONTRIBUTING.md)).

**После каждого коммита:** `cargo build --release && cargo test && cargo clippy --release`.

**После каждого этапа:** сравнить размер exe и число тестов с базой, пройти ручной прогон затронутых вкладок.

**Критерий готовности:** все тесты зелёные, предупреждений не больше исходного, exe в пределах допуска, ручной прогон без отличий, в `src/` нет файлов больше 800 строк (кроме оговорённых).

## 8. Процесс в git

- Отдельная ветка `refactor/split-modules` от `main`, каждый этап — серия коммитов.
- Слияние локально, без GitHub: `git switch main && git merge --no-ff refactor/split-modules`. Перед слиянием просмотреть `git log --stat main..refactor/split-modules` и `git diff main...refactor/split-modules`.
- Для проверки «перенос не менял код»: `git diff --color-moved=dimmed-zebra -M` показывает перемещённые блоки отдельным цветом, так проще убедиться, что менялись только пути и видимость.
- Релиз и версию в этой работе не поднимать: для пользователей ничего не меняется.

## 9. Риски

| Риск | Что делать |
|---|---|
| Поля `Ui`/`App` нужны сразу нескольким файлам | `pub(super)`; не вводить геттеры ради геттеров |
| Циклические `use` между подмодулями | общее — в `mod.rs` или в самый нижний подмодуль |
| Нарушение порядка инициализации `static`/`thread_local` | переносить только объявление вместе с использованием, порядок вызовов не трогать |
| Рост размера exe | сравнивать после каждого этапа; при росте больше 1% выяснить причину |
| Конфликт слияний, если параллельно идёт другая работа | пока идёт рефакторинг, новые функции не добавлять в затрагиваемые файлы или делать после слияния |

## 10. Что вне рамок

- Переписывание логики, смена алгоритмов, оптимизация.
- Смена библиотек и зависимостей.
- Разбиение файлов меньше 450 строк.
- Создание трейтов, слоёв абстракции и кроссплатформенности «на будущее».
