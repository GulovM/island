# Kite Island — инструкции для Claude Code

## Проект
GPU-рисуемый (Direct2D) «остров» для Windows 10/11, чистый Rust, без веб-стека.
Жёсткие бюджеты (CONTRIBUTING.md): CPU в простое ≈ 0%, RAM ≤ 60 МБ (пик по замерам ~55 МБ), exe ≤ 3 МБ,
минимум зависимостей (сейчас только крейты семейства `windows-rs`). Точка входа — `src/main.rs`.

## Рабочий процесс: реализация делегируется, Claude всегда проверяет
Для задач, попадающих в зону одного из под-агентов ниже (`.claude/agents/agy-*.md`),
реализацию делает соответствующий под-агент через agy. Claude не правит код в обход
агента для таких задач молча — он делегирует, затем **обязательно сам читает diff**,
а не ограничивается прогоном тестов/clippy. Для мелких точечных правок вне зоны
под-агентов (конфиги, CI, докстроки) Claude может править сам.

Не упоминать agy в `docs/`, README, issues/PR-текстах — это внутренняя деталь
`.claude/`. Коммиты — без `Co-Authored-By` / `Generated-with` строк.

### Цикл на каждую задачу
1. Определить зону по затронутым файлам (таблица ниже); для сквозных задач — несколько
   агентов по очереди, каждый со своей частью.
2. Агент формулирует agy самодостаточную задачу (agy не видит историю диалога) и
   запускает её.
3. После завершения агент сам гоняет `cargo build`, `cargo clippy --all-targets --
   -D warnings`, `cargo test` и чинит очевидные ошибки компиляции — это не заменяет
   ревью, а экономит круг.
4. Claude (вызывающий, не под-агент) проверяет результат:
   - читает `git diff` целиком, построчно, а не по диагонали;
   - для визуальных/анимационных изменений — живой запуск с изолированным
     `$env:APPDATA` (дождаться закрытия предыдущего экземпляра) и короткая проверка
     скриншотом — остров перехватывает курсор, долго не держать открытым;
   - прогоняет ревью-скиллы/агентов из таблицы ниже на изменённых файлах;
   - проверяет бюджеты и ограничения (раздел «Что ловит ревью»).
5. Если есть замечания — задача уходит обратно тому же под-агенту с конкретным
   списком (файл:строка, что не так, что исправить), не общими фразами. Повтор, пока
   чисто.
6. Коммит — только по явной просьбе пользователя, без атрибуции Claude.

### Под-агенты и их зона

| Агент | Зона кода | Скиллы для реализации | Ревью после agy |
|---|---|---|---|
| `agy-ui` | `src/ui/*`, `face.rs`, `theme.rs`, `glass.rs`, `render.rs`, `gfx.rs`, `icons.rs`, `tabs/*` (вёрстка/стили) | `frontend-design`, `apple-design`, `ui-ux-pro-max:ui-styling`, `break-ui` | `code-review`, `emil-design-eng`, `break-ui` |
| `agy-motion` | `anim.rs`, морфинг/blur в `glass.rs`, `dnd.rs`, `dragdrop.rs`, переходы в `tabs/*` | `animate`, `animation-performance`, `apple-design`, `ecc:motion-foundations`, `ecc:motion-patterns` | `review-animations`, `animation-performance` |
| `agy-backend` | `bg/*`, `online/*`, `sys/*`, `config.rs`, `state.rs`, `update.rs`, `live.rs`, `backdrop.rs` | `ecc:rust-patterns`, `security-review` | `ecc:security-review`, `code-review` |

Финальный проход по **всему** диффу независимо от зоны — `code-review` (уровень
`medium` по умолчанию, `high`/`max` только если явно попросили) и, для unsafe/FFI к
Windows API, `ecc:security-review`/`security-review`.

### Модель Claude для суб-агентов (экономия лимитов; не модель, которую использует `agy` внутри)
Это правило — про суб-агентов, которых **эта сессия Claude** запускает через
Agent-инструмент (`agy-ui`/`agy-motion`/`agy-backend`, а также общие `Explore`,
`general-purpose`, `ecc:rust-reviewer`, `ecc:security-reviewer`, `ecc:rust-build-resolver`,
`claude-code-guide` и т.п.). Оно **не** про модель, которую использует **сам `agy`**
внутри себя для генерации кода — у него своя линейка (`claude-sonnet-4-6`,
`gemini-3.8-flash-high`), выбирается по правилу из раздела «Как вызывать agy» ниже
(бюллет «Модель по умолчанию»), и это отдельный, не связанный с лимитом текущей
сессии ресурс.

**Потолок — `model: "sonnet"` (Sonnet 5.5) с `effort: "high"`.** `opus` и `fable` в
этом проекте не использовать вообще — они выше потолка. `effort: "high"` на `sonnet`
держать только для **по-настоящему значимых** ситуаций (см. таблицу) — для остальных
sonnet-задач `effort: "medium"` справляется не хуже и дешевле.
**Пол и модель по умолчанию — `model: "haiku"` (Haiku 5.5) с `effort: "medium"`.**
Для большинства задач ниже использовать именно его — так лимиты расходуются
экономнее. Это и задано статически в frontmatter каждого `.claude/agents/agy-*.md`
(`model: claude-haiku-5-5`, `effort: medium`).

При вызове Agent-инструмента явно передавать `model` (и `effort`, если нужно
поднять/опустить относительно умолчания агента) — так эскалация переопределяет
frontmatter точечно, на один вызов, не трогая дефолт самого агента.

| Триггер / агент | Модель | Effort | Почему |
|---|---|---|---|
| `agy-ui`/`agy-motion` — типовая точечная правка (конкретный файл:строка, ясный критерий приёмки) | `haiku` | `medium` | Рутинная механическая задача, низкий риск |
| Rework-раунд по конкретным замечаниям ревью (файл:строка, что исправить) | `haiku` | `medium` | Та же механика, что и исходная задача — не архитектурное решение |
| `Explore`/`general-purpose` — найти файл/функцию/использование в коде | `haiku` | `medium` | Поиск, не оценка качества |
| `claude-code-guide`, рутинные справочные вопросы | `haiku` | `medium` | Информационный лукап, не кодогенерация |
| `ecc:rust-build-resolver` — починка ошибок компиляции/clippy | `haiku` | `medium` | Механическая правка по сообщению компилятора |
| `agy-backend` — типовая интеграция с внешним API/источником данных без unsafe-поверхности (например online/*, обычный `Result`-код) | `haiku` | `medium` | Рутинная задача, пока не тронут unsafe/Windows API |
| `agy-motion` — сложный многошаговый переход (несколько связанных пружин/фаз, как `peek`/drag-инерция) | `sonnet` | `medium` | Не механическая правка, цена логической ошибки в state machine выше |
| `agy-ui` — изменение, затрагивающее несколько связанных файлов вёрстки/стиля сразу | `sonnet` | `medium` | Больше площади для несогласованности, чем в точечной правке |
| Повторный rework после того, как `haiku` не справился с задачей/не понял замечание | `sonnet` | `medium` | Поднимаем тир модели, а не сразу effort — `high` только если и `sonnet`/`medium` не находит/не исправляет |
| `agy-backend` — unsafe/FFI к Windows API (`sys/*`, `backdrop.rs`, `uia.rs`, `registry.rs`, `shell.rs`), реестр/clipboard/UIA | `sonnet` | `high` | Эквивалент «цены пропущенной уязвимости» в этом проекте — ошибки здесь дороже, чем в UI, трогают систему пользователя |
| `ecc:security-reviewer`/`security-review` на unsafe/FFI-диффе | `sonnet` | `high` | Та же причина — security-критичная поверхность |
| Архитектурно значимые решения (смена схемы рендера, pluggable-источник данных, `agy --mode plan`) | `sonnet` | `high` | Неоднозначные требования, высокая стоимость отката |
| Диагностика бага в главном цикле/тайминге (`main.rs`, события, таймеры) — цена ошибки системная, не локальная | `sonnet` | `high` | Ошибка здесь способна тихо сломать несвязанную фичу (пример — баг `dt` в главном цикле) |

Если задача не попадает явно ни в одну строку — по умолчанию `haiku`/`medium`;
поднимать до `sonnet` только при реальном сигнале риска (unsafe/Windows API,
архитектурная неоднозначность, повторный провал на `haiku`), а внутри `sonnet`
держаться `medium` и переходить на `high` только для по-настоящему значимых случаев
из последних четырёх строк таблицы — не «на всякий случай».

### Как вызывать agy — шаблон
`agy -p` (print/headless-режим, используемый здесь для неинтерактивного запуска из
Bash) **не может показать интерактивный запрос на подтверждение** инструмента
(запись файла, выполнение shell-команды). Без обхода этого запроса любой вызов
инструмента внутри `agy` автоматически отклоняется, и `agy` завершается без единого
изменения с ошибкой вида:

```
jetski: no output produced — a tool required the "command" permission that headless mode cannot prompt for, so it was auto-denied.
```

Поэтому `-p`/headless-запуск **обязательно** требует `--dangerously-skip-permissions`:

```bash
agy -p "<задача> | Acceptance: <конкретный критерий приёмки> | Используй скиллы: <релевантные ecc:*-patterns, если применимо> | Не выходи за бюджеты (CPU простой ≈ 0, RAM ≤ 60 МБ, exe ≤ 3 МБ, зависимостей сверх семейства windows-rs не добавлять)" \
    --mode accept-edits \
    --dangerously-skip-permissions \
    --add-dir "D:/Desktop/Files/mainnew/island" \
    --output-format text
```

Это безопасно в нашей схеме, потому что результат в любом случае проходит ревью по
реальному diff перед коммитом (цикл выше) — флаг даёт agy свободу действий внутри
рабочей копии, а не право решать, что попадёт в итог без проверки.

**Если Claude говорит, что не может запустить `agy` даже с
`--dangerously-skip-permissions`** — это почти всегда **не** ошибка `agy`, а другой,
более ранний уровень разрешений: самому Claude Code нужно подтверждение на запуск
Bash-команды (`agy ...` как таковой), прежде чем `agy` вообще стартует. Если сессия
неинтерактивна или это разрешение не преднастроено — Bash-вызов блокируется раньше,
чем флаг `agy` успевает что-то решить. Это две разные, не связанные друг с другом
системы разрешений:
1. Разрешения Claude Code на запуск Bash-инструмента (`agy ...` как команда) —
   настраиваются в `settings.json`/`settings.local.json` (allow-rules) или
   подтверждаются вручную в интерактивной сессии.
2. Разрешения самого `agy` на внутренние вызовы инструментов (запись файлов, shell) —
   решаются флагом `--dangerously-skip-permissions`.

Если встретили это — не пытаться «обойти» добавлением ещё одного флага к `agy`;
нужно либо подтвердить Bash-вызов вручную (в интерактивной сессии), либо попросить
пользователя разрешить команду `agy` через allow-rule в `settings.json` (см. скилл
`update-config`), и только после этого `agy` с `--dangerously-skip-permissions`
сможет реально отработать.

Для долгих задач — запускать в фоне (`run_in_background`/`&`) и перенаправлять вывод
в лог-файл, иначе результат не попадёт в контекст:

```bash
agy -p "..." --mode accept-edits --dangerously-skip-permissions --add-dir "D:/Desktop/Files/mainnew/island" --output-format text > /path/to/log.txt 2>&1
```

- `--mode accept-edits` — для доверенных, хорошо специфицированных задач (большинство
  задач в таблице выше).
- `--mode plan` — использовать первым проходом для архитектурно значимых задач
  (например, смена схемы рендера, pluggable-источник данных), чтобы увидеть план до
  правок, затем подтверждать. План выводится в stdout (или в отдельный markdown-
  артефакт, на который `agy` даёт ссылку) — прочитать его перед тем, как давать добро
  на реализацию.
- Чтобы продолжить тот же диалог `agy` (например, подтвердить план или отправить
  rework после ревью) — использовать `-c`/`--continue` **в той же рабочей
  директории** (`agy` привязывает историю к cwd), не начинать новый `-p` с нуля:
  ```bash
  agy -c -p "План подтверждён, реализуй... / Ревью нашло проблемы: ... исправь..." --mode accept-edits --dangerously-skip-permissions --add-dir "D:/Desktop/Files/mainnew/island"
  ```
- Модель по умолчанию — `claude-sonnet-4-6` для backend/security-критичных задач
  (`agy-backend`); `gemini-3.8-flash-high` допустим для рутинных/шаблонных задач
  (мелкие UI-правки, иконки, i18n-строки) — экономия при сопоставимом качестве для
  простых задач.
- Rework-промпт формулируется так же, через `-c -p`, но с перечислением конкретных
  найденных проблем (файл, строка, что не так) вместо исходной задачи.
- Не доверять самоотчёту `agy` о «живой» проверке (запуск острова, тесты и т.п.),
  если среда, где он работал, могла не иметь доступа к нужным ресурсам (сеть, живой
  Windows-сеанс) — проверять такие вещи самостоятельно после ревью, перед коммитом.

### Что ловит ревью (отказывать agy, если нашёл)
- Новые таймеры/поллинг, будящие процесс в простое; заметный рост RAM/размера exe.
- Новые зависимости без явного обсуждения с пользователем — в Cargo.toml сейчас
  только `windows-rs`.
- Небезопасный/некорректный unsafe и работа с Windows API (`sys/*`, `backdrop.rs`,
  `uia.rs`, `registry.rs`, `shell.rs`) — обязательно отдельный security-проход.
- Комментарии/сообщения не на русском или английском, не в стиле окружающего кода,
  либо описывающие «что» вместо «почему» (CONTRIBUTING.md).
- Любой диф, который проходит тесты/clippy, но не был прочитан построчно самим
  Claude — тесты зелёные не означают «без замечаний».
